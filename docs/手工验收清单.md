# 手工验收清单

自动化测试覆盖的是逻辑（412 项，跑 `npm run test:all`），覆盖不到的是**这些状态在真实浏览器里
会不会遮挡、关不掉、或者让人误解**，以及**窗口开出来能不能真的敲进去**。这一轮专门走这些。

背景：`src/store/AppContext.jsx` 里的启动核对、防抖双写、页面隐藏时落镜像都写在 effect 里，
SSR 测试不执行 effect，所以这部分只有人眼能验。

---

## 准备

```bash
cd E:\githubxiangmu\ai-workbench
npm run dev
```

两个端口都要留意：**5173 是前端，5174 是接口**。改了后端代码后如果没生效，
多半是旧进程还占着端口（`concurrently` 的子进程不会跟着父进程一起被杀）。

查看端口占用（在 **PowerShell** 里跑，`grep` 不可用）：

```powershell
netstat -ano | findstr :5174
netstat -ano | findstr :5173
```

按 PID 杀进程：

```powershell
taskkill /PID <上面查到的PID> /F
```

或一步到位：

```powershell
Get-NetTCPConnection -LocalPort 5174 -State Listen |
  ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

在 Git Bash 里才可以用 `grep`：

```bash
netstat -ano | grep -E ":5174|:5173" | grep LISTENING
```

数据文件在 `~/.ai-workbench/data.json`（用户目录下的隐藏目录，Windows 上是 `C:\Users\<你>\.ai-workbench\data.json`）。
想从干净状态开始，直接删掉这个文件即可。

## 场景 2 · 离线横幅

**怎么触发**：把 5174 的进程杀掉，只留前端。

更省事的办法 —— 停掉一切，只起前端：

```bash
npm run dev:web
```

| # | 步骤 | 期望 |
| --- | --- | --- |
| 2.1 | 只起前端，打开页面 | 顶部出现橙色横幅，说明改动只存在浏览器里、跑 `npm run dev` 后会落盘 |
| 2.2 | 改点东西 | 改动**照常生效**（不能因为服务没起来就没法用） |
| 2.3 | 看设置页 | 保存状态是橙色「本地服务未启动」，三个按钮都置灰 |
| 2.4 | 恢复 `npm run dev`，**不要刷新页面**，等 5 秒左右 | 横幅消失，弹出「本地服务已恢复，正在把改动补写到磁盘」，状态变绿 |
| 2.5 | 恢复之后再改一次 | 正常写入，状态短暂变「有改动待写入」后回绿 |

**要盯的**：

- [ ] 横幅会不会盖住页面顶部内容；文字会不会太长换行难看
- [ ] 服务恢复后状态**自动**变回绿色，不需要手动刷新
- [ ] **停掉接口之后改动时，不应该弹任何 Toast** —— 只有横幅提示就够了。
      这条是回归点：之前接口一停，每次改动都会弹一条「服务返回了非 JSON（500）」，
      既误报（离线是正常降级，不是错误）又重复。

### 2 号场景的回归背景

两个叠加的原因，都在这一轮修了：

1. **误判**：接口挂掉时 Vite 代理返回的是 `500 + text/plain` 错误页（实测确认），
   `res.json()` 直接抛，被归类成「服务返回了非 JSON」。但这不是「服务返回坏数据」，
   是「服务不在」—— 现在归一到 `SERVICE_OFFLINE`，由横幅统一承担提示。
2. **状态没跟上**：服务是**中途**挂掉的，而 `disk.available` 还停在启动时的 `true`，
   所以每次保存都真的去发请求、每次都失败、每次都弹。现在失败后会把 `available`
   置回 false，后续保存直接短路。

自动化覆盖：`isServiceOffline` 的 8 种状态/Content-Type 组合，以及走真实请求路径的
4 种响应（代理错误页 / 接口自己的 JSON 错误 / 正常 200 / 连接被拒），共 13 项。

## 场景 3 · 启动恢复（重点）

**怎么触发**：制造「浏览器里的版本比磁盘新」的局面。

> ⚠️ **注意**：页面**开着**的时候不会出现这个弹窗。离线后服务一恢复，
> 5 秒内探针会自动重连并把改动补写回磁盘，分歧就被抹平了（这是自愈，是想要的行为）。
>
> 所以要触发恢复弹窗，必须在离线状态下**把标签页整个关掉** —— 关掉就没有探针了，
> 本地镜像停在较新的版本，下次打开才会出现分歧。
>
> 这也正是这个弹窗存在的理由：用户离线时改了点东西就直接关了电脑，
> 这类情况探针够不着，只能靠启动核对。

| # | 步骤 | 期望 |
| --- | --- | --- |
| 3.1 | 正常启动，等状态变成「已写入磁盘」 | 基线建立好了 |
| 3.2 | 杀掉 5174 的进程（只杀接口，前端留着） | 顶部出现橙色离线横幅 |
| 3.3 | 改点东西 —— 比如新建一个项目、改个名 | 改动生效，横幅还在 |
| 3.4 | **把标签页整个关掉**（不是刷新，是关掉） | —— |
| 3.5 | **重启接口**：`npm run dev` | —— |
| 3.6 | 重新打开 http://localhost:5173 | **弹出恢复对话框** |
| 3.7 | 看对话框里的两栏数字 | 浏览器那栏应该比磁盘那栏多（多出第 3.3 步的改动） |
| 3.8 | 点「恢复浏览器的改动」 | 第 3.3 步的改动保留，状态回到「已写入磁盘」 |
| 3.9 | 重复 3.2–3.6，这次点「用磁盘上的版本」 | 第 3.3 步的改动消失，回到磁盘那版 |

**顺带验一下自愈**（不算场景 3 本身，但值得看一眼）：

| # | 步骤 | 期望 |
| --- | --- | --- |
| 3a.1 | 正常启动，杀掉接口，改点东西 | 橙色横幅 |
| 3a.2 | 重启接口，**不关页面也不刷新**，等 5 秒 | 横幅自动消失，提示「本地服务已恢复」 |
| 3a.3 | 刷新页面 | **不出现**恢复弹窗（改动已经补写进磁盘了） |

**要盯的（这是本轮最需要人眼判断的地方）**：

- [ ] 弹窗**能不能关掉**？正确行为是：右上角**没有 ✕**，按 Esc **不关**，点外面**不关** ——
      必须点底部两个按钮之一。如果发现能绕过，说明 `dismissible={false}` 没生效。
- [ ] 两栏数字**对不对得上**？浏览器那栏显示的是本地镜像的统计，磁盘那栏是磁盘的。
- [ ] 文字有没有说清楚「选哪个会丢什么」？特别是「用磁盘上的版本」会丢东西这件事。
- [ ] 弹窗在**窄屏**（把窗口拉到 400px 宽）会不会溢出？两栏应该变成上下堆叠。
- [ ] **如果有 Toast 同时弹出**（比如第 3.4 步的「已从磁盘加载」），它会不会盖住弹窗底部的按钮？
      预期是：弹窗开着时 Toast 会自动挪到**顶部**。这条是特意为防卡死加的，务必确认。

## 场景 4 · 版本冲突（两个标签页）

这是回归测试 —— 之前这里有个丢失更新的 bug，已修，需要确认修好了。

| # | 步骤 | 期望 |
| --- | --- | --- |
| 4.1 | 同一个地址开**两个标签页** A 和 B | 两个都显示同样内容 |
| 4.2 | 在 A 改一个项目名，等它保存完 | A 状态变绿；**先不要动 B** |
| 4.3 | 切到 B，改另一个项目名 | **弹出冲突 Toast**，B 顶部出现红色横幅「写入已停止」 |
| 4.4 | 看 A 和 B 的数据文件 | 检查 `data.json`，A 的改动应当在；B 的改动**没有**覆盖掉 A |
| 4.5 | 在 B **再改一次**，看会不会又弹一条 Toast | **不应该重复弹** —— 红色横幅已经在提示了 |
| 4.6 | 在 B 点 Toast 里的「处理冲突」 | 弹出确认框，说明重新加载会丢掉本地改动 |
| 4.7 | 确认后 | B 变成磁盘版本（含 A 的改动），状态回绿 |
| 4.8 | 回到 A，改点东西 | A 正常写入，不再冲突 |

**要盯的**：

- [ ] 冲突 Toast 会不会自动消失得太快？（带操作按钮的应该留 12 秒）
- [ ] 如果 Toast 消失了，**顶部红色横幅还在不在**？（必须还在，否则用户就失去线索了）
- [ ] **重复进入冲突状态不应该重复弹 Toast**（第 4.5 步）。只在该进入时提示一次，
      之后靠横幅。这是回归点 —— 和场景 2 里「服务一停就每次改动弹一条」是同一类噪音。
- [ ] 「处理冲突」点下去之后，是**先确认再执行**，还是直接就把本地改动丢了？
      正确行为是先确认。
- [ ] 提示文字有没有说清楚**两边分别是什么**？光是「冲突了」不够，得让人知道该选哪个。

## 记录方式

发现问题时记下四件事：

1. **场景编号**（比如 3.6）
2. **怎么触发的** —— 步骤要能复现
3. **看到了什么** —— 截图最好
4. **期望是什么**

如果某一项**触发不出来**（比如按步骤走但没出现恢复弹窗），这本身也是问题，
要记下来 —— 说明状态机的某个分支没走到，逻辑测试覆盖了 `decideBoot`，
但 AppContext 里的接线没被验证过。

### 「不能过少」是硬指标（8.19 起）

下限写进了提示词，生成后还会**服务端校验**，不达标自动重来一次。要确认这套真在起作用。

| # | 步骤 | 期望 |
| --- | --- | --- |
| 8.19 | 对一个新项目点「让 AI 拆解项目」 | **不少于 6 步**；覆盖了「定交付标准 → 准备 → 主体（能各自独立开工）→ 验证 → 整理交付」；每步都有「要做什么」和「算完成」 |

| 8.21 | 数一下条数 | 十来步的项目应该有二三十条。**只有几条说明上限或校验有问题** |
| 8.22 | 换一个**完全不同的领域**再走一遍（比如把摄影作业换成「写一份商业计划书」或「搭个人网站」） | 步骤和知识点**依然贴那个项目**，不是套模板；覆盖依然完整 |
| 8.23 | 看生成耗时 | 十几到二十几秒正常（第三方端点）。如果到三十秒以上，多半是触发了「重试」—— 此时**必须**有一条说明为什么的提示，不能悄悄多花时间还不说 |

**要盯的**：

- [ ] **8.22 是这一组的关键**：这套下限必须是**通例**，不是只在某一个领域上调好的。
      换个领域就退回泛泛而谈，说明提示词还是绑在具体项目上了
- [ ] **8.23**：触发重试时如果**没有任何提示**，那就是静默失败 —— 用户只会觉得「今天特别慢」
- [ ] **8.20** 那条如果出现某一步空白，看有没有如实报出来（「这些步骤一条知识点都没分到…」）。
      报出来是及格，悄悄放过是不及格

**要盯的**：

- [ ] **8.5 / 8.10 / 8.11 / 8.12 的标签都必须是实际模型名**。走兼容端点却标「由 Claude 生成」
      就是界面在说假话 —— 这条以前真出现过，现在改成显示真实模型名了
- [ ] **8.8 和 8.9 是一对**：错误要能自解释。如果 8.8 的失败看起来没头没脑，说明错误归类还不够
- [ ] **每次生成都要能一眼看出是真实模型还是模拟数据**。这是最关键的一条 ——
      如果真实调用失败了却悄悄给模拟数据、界面不标，用户会以为模型真生成了这些内容
- [ ] 真实生成的结果里，`reasonNeeded` / `doneWhen` 要落到项目本身上，不是套话
- [ ] 出结果慢的时候有没有加载态（第三方端点可能要十几秒），别让人以为卡死了
- [ ] **兼容模式偶尔会失败**：它没有硬保证，模型不听话时仍会退回模拟数据并说明。
      连试两次都是模拟数据才算问题

## 场景 9 · 命令行类型在新终端里运行

这轮改了命令行类型的启动方式。原来走 `detached + stdio:ignore`，起的进程既没有控制台也没有
输入，**交互式程序起来就死**（`claude` 实测：spawn 事件触发 → 后端返回 `ok:true` → 前端弹
「已启动」→ 桌面上什么都没出现）。现在经 `cmd.exe /c start` 在新终端窗口里跑。

自动化覆盖的是判定顺序和错误码（`npm run test:launch`，30 项），**「窗口真的开出来了、
而且能敲进去」只能人眼看**。

| # | 步骤 | 期望 |
| --- | --- | --- |
| 9.1 | Agent 管理里新建命令行类型，命令填 `claude`，参数留空，保存 | —— |
| 9.2 | 点「打开」 | **弹出一个真的终端窗口**，`claude` 在里面正常启动 |
| 9.3 | 在那个窗口里输一句话回车 | 有正常回应 —— 证明不是个死窗口 |
| 9.4 | 关掉窗口，回工作台再点一次「打开」 | 每次都是新窗口，互不影响 |
| 9.5 | 设置页把 `aiwb-not-installed-xyz` 加进可信命令，再去新建一个 Agent 用它，点「打开」 | 红色 Toast：**系统里找不到「aiwb-not-installed-xyz」这个命令** |
| 9.6 | 命令用 `claude`，参数填一行 `a&b`，点「打开」 | 红色 Toast：**参数里的「a&b」会被终端当成语法** |
| 9.7 | 打开你现有的「本地 Python」（`python -i`） | 新终端里出现 Python REPL，能敲 `print(1)` |

**要盯的**：

- [ ] **9.2 / 9.3 是这轮最关键的一条**：进程活着不等于能用。窗口得真的能敲进去
- [ ] **9.6 拒绝的时候不能有任何窗口闪出来** —— 参数守卫必须在启动之前生效，不是起来再关
- [ ] **9.9 是回归点**：`explorer.exe` 把手头工作交接给已运行的资源管理器后会自己退出，

- [ ] Toast 里显示的**命令名**是不是你实际填的那个（不是内部解析出来的绝对路径）

**这轮没验的部分**：非 Windows 平台。开终端的方式各平台不同，没有环境验，所以没写 ——
非 Windows 上命令行类型维持直接 spawn 的老行为，交互式程序仍然起不来。见 README 第 3 条。

## 已知的行为，不算 bug

- 磁盘文件损坏时（手动把 `data.json` 改成非法 JSON），会另存为 `data.corrupt.json`，
  然后退回浏览器镜像，顶部提示。**原始文件不会被覆盖**，这是故意的。
- 服务没起来时改动照常可用，只是不落盘。这是有意的降级，不是故障。
- `reveal`（打开数据目录）在生产模式下返回 404。要开就设 `AIWB_ALLOW_REVEAL=1`。

### 两个标签页 + 未处理冲突就直接刷新 = 改动静默消失

两个标签页**共享同一份 localStorage**（同源）。所以标签页 B 冲突之后，如果不点「处理冲突」
就直接刷新 B，B 会静默回到磁盘版本，那笔没写进去的改动消失且无提示。

原因：版本号是单个计数器。A 从第 3 版改到第 4 版，B 从第 3 版改也算出第 4 版，
两个 `4` 撞在一起，刷新时 `镜像版本 == 磁盘版本` 被判成「已同步」，分歧就不可见了。

**影响范围**：仅限「B 冲突后不处理直接刷新」这一条路径。冲突时红色横幅是常驻的，
正常操作不会走到这里。

**要根治**需要给版本号加客户端标识（`{计数器, 客户端id}`），让两个客户端的版本号不会碰撞。
对个人本地工具来说偏重，暂记为已知限制。如果实际用起来真的踩到了，再补。
